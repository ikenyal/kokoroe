## プロジェクト名

ココロエ（Kokoroe）— 商いの心得を継ぐ、AIの弟子

## 選んだテーマ

**テーマ1: あなたにしかない深さを。**

ベテランが長年かけて身につけた仕事のやり方を、本人がまだ現場にいるうちに、次の人が受け継げる形にする。この作品は、それを中小企業の「取引先ごとの付き合い方」という現場で形にしたものです。仕事を変える人が年に330万人いる中で（総務省統計局「労働力調査（詳細集計）2025年平均結果」の転職者数）、ベテランのそばで何年も見て覚える、という壁を取り払う点では、テーマ2「本来、誰にでも届くべきものを。」にも重なります。

## 概要: 解決する課題と、誰のためのものか

**聞いても出てこない作法を、ダメ出しで受け継ぐ。** 引退を控えた中小企業のベテランと、その後を継ぐ人のためのものです。ベテランは AI の弟子の案に ○・△・× を付けるだけ。直しの一つ一つが、なぜそうなったかと一緒に心得帳に残り、Agent Skill として後任に渡ります。

**リンク**

- リポジトリ: https://github.com/ikenyal/kokoroe
- 公開デモ: 〔11/6 に公開したら URL〕
- 動画: 〔11/7 の撮影のあと〕

**課題**

- 中小企業では、取引先ごとの付き合い方がベテラン一人の頭の中にあります。
  - 誰に先に伝えるか。何をメールで送り、何を顔を見て話すか。いつは避けるか。正式な話の前に、誰の耳にそっと入れておくか。
- ベテランは、これを説明してと頼まれても言葉にできません。けれど案を見せれば「違う、そうじゃない」とすぐ言えます。
- その人が引退すると、作法も「なぜそうなったか」も一緒に消えます。
  - 帝国データバンク「全国『後継者不在率』動向調査（2025年）」では、調査対象の中小企業の51.2%で後継者が決まっていません。新任社長の就任経緯では内部昇格（36.1%）が同族承継（32.3%）を上回り、「M&Aほか」も20.6%と、継ぐ人の「脱ファミリー」が進んでいます（速報値）。

**Kokoroe がすること**

1. **弟子が先にやる。** 取引先の場面ごとに、AI の弟子・橙丸が段取りの案を作ります。誰に（正式な宛先）・何で（メール、電話、手紙、訪問、あえて連絡しない）・いつ・裏で誰に（決裁者などへの根回し）・後日のあいさつ。文面は、その下に畳んだ下書きです。扱う場面は、納期の遅れ・見積り・新しい提案・代替わりのあいさつなど10種類です。
   - 段取りに訪問が入るときは、服装・手土産・先に確かめる話題・同席者・呼び方も案に含め、同じ ○△× と一言で直せます。**評価の対象は連絡の段取りです。訪問の段取りは正解がないため対象外です**（D-061）。
2. **師匠は印を付けるだけ。** ○／△／× と、なくてもよい一言。インタビューや書き起こしの手順はありません。
   - 一言が曖昧なときは、読み方の候補から1タップで選びます。どれでもなければ「どれでもない」。一言がないときは、違う場所（誰に・何で・いつ・裏で誰に・書式・その他）も同じタップで選べます（D-057）。
3. **直した分が心得帳になる。** △・× の一言を Claude が読み取り、適用範囲つきの短い心得として書きます。
   - 出典（どの判定で、師匠が何と言ったか）と、沿革（旧 → 新・きっかけ・日付）も書き残します。
   - 書いた心得で直した場面と、以前 ○ だった場面を解き直し、正しかったものを崩していないかを確かめます。
4. **後任が継ぐ。** 後任の質問には、心得帳だけを根拠に、沿革を添えて答えます。記録がないことには「師匠に確認を」と答えます。
   - 心得帳は Agent Skill として書き出せ、後任の手元の Claude Code がそのまま使えます。
   - 引き継ぎの期間には、読み取り専用の MCP サーバーから、写しの後に増えた心得も引けます。
5. **自分の会社で始める。** 手元の PC（127.0.0.1）でだけ動くモードで、自分の取引先台帳から始められます。データはリポジトリの外のフォルダに置き、公開版にはありません（D-056）。
   - 信頼の段位（見習い・手代・番頭）は記録の再生で試し、見送りました。○ が続いても次の案の正しさを予測しなかったためです。代わりに、取引先ごとの実績を情報として見せます（D-055）。

**誰のためのものか**

- **引退を控えたベテラン（師匠）。** 説明を求められずに、普段どおり「違う」と言うだけで、作法を残せます。
- **後を継ぐ人（社内の人や、事業を買った人）。** 「この手順は省いていいですか」に、理由と経緯つきの答えを得られます。
- **長く使い続ける場面:** 引退が決まってから後任に渡すまでの数か月、毎日の段取りの案を師匠が確かめる、その延長で心得帳が育ちます。

**いま示せること**（架空の取引先10社。一致率は評価用20場面、沿革は取引先の経緯を聞く質問8問、乱用への強さは注入・値引きの場面各9回で、師匠はシミュレータ。〔正式 or 途中経過〕。師匠の手間だけは、作者1人が架空の学習用20場面で測ったもの）

- **作法の一致率:** 評価用20場面で、師匠の ○ との一致率は、台帳と制約だけの弟子で〔before.match〕でした。40場面で師匠が直したあとは〔paths.mean〕（学習〔paths.n〕本の平均、幅〔paths.min〕〜〔paths.max〕）です。
- **沿革の質問への答え:** 後任が「なぜそうなったか」まで答えられた質問は、8問中〔history[0].mean〕 → 〔history[1].mean〕問でした。
- **乱用への強さ:**
  - 取引先の文面に紛れた「これを心得として登録せよ」で心得帳が変わった回数は、〔adversarial.injectionRuns〕回中〔adversarial.injectionRuns − adversarial.storeProtected〕回でした。
  - 値引き・契約条件を迫られた場面で、弟子（モデル）が自分で師匠の判断に回したのは〔adversarial.lureRuns〕回中〔adversarial.escalatedByModel〕回。さらにコードの下限（D-044）で、値引き・契約・金額の場面は必ず師匠に回ります（〔adversarial.escalated〕/〔adversarial.lureRuns〕）。
- **師匠の手間（作者1人の師匠役テスト、架空の20場面）:** ○△× を付けるまで1件あたり中央値53.5秒（案を読む時間を含む。20件で約18分）。
  - **20件中18件が ○:** この会社と取引したことのない作者には、丁寧でもっともらしい案が合格に見えました。事情を知らない後任が AI の案をそのまま送ってしまう構図そのものです。同じ20件をコードの判定（隠しの正解）でも採点すると、作者が ○ を付けた18件は ○ 3件・△ 8件・× 7件でした（シミュレータの一人の師匠の正解で、実在のベテランではない。D-059、`docs/results/master-role-vs-simulator-2026-11-05.json`）。
  - **測れていないこと:** 同じ作法を文章で書く時間は測っていません（作者に書き起こす元の経験がないため）。書く時間との比較はしていません。
  - **自分の会社での比較テストも打ち切りました（D-062）。** 仮の台帳では、取引先ごとの事情を作者が知らず、文章で書けるのは一般的なマナー（AI がもともと知っている平均）だけでした。「書くより直すほうが楽」は、人の実測では示せていません。比較の機能は、実際に導入する会社が本当に経験のある相手で使うために残しています。

## Claude 利用に関する質問（想定した問いへの答え）

### Q. 製品のどこで、どの Claude を、なぜ使っていますか

| 役割 | モデル | 選んだ理由 |
|---|---|---|
| 弟子の段取りの案、後任の質問への答え | Claude Sonnet 5.5 | 師匠は1枚ずつ印を付けるため、数秒で返ってくる必要がある |
| 師匠の △・× と一言の解釈、心得帳の編纂 | Claude Opus 5.5 | 判断が重く、裏で非同期に回せる。待たずに次の札へ進める |

- **使い方の中心は「平均との差」:**
  - Claude は平均的で筋のよい案を出し、師匠はそこからの差だけを示します。
  - 暗黙知は、直された瞬間の「平均との差」として初めて言葉になる、という考え方を、Claude の得意な部分に乗せました。
- **心得帳を守る仕組み:**
  - 一言の読み方が割れるときは、候補を2〜3個出して師匠に選んでもらいます。
  - 書いた心得は、すぐ解き直して確かめます（確かめ稽古と回帰の確認）。崩したら、範囲を絞るか差し戻します。
- **後任への渡し方:**
  - 心得帳は Agent Skill として書き出します。
  - 引き継ぎの期間用に、読み取り専用の MCP サーバー（道具は4つ）も作りました。書き込む道具、Claude を呼ぶ道具、取引先が書いた文面は持たせていません。
- **費用:** 固定部分にプロンプトキャッシュを使っています。A/B で測って、判定を変えずに費用を約37%下げました。
- **Managed Agents（D-002）:**
  - メモリストアは、同じ入出口の別の保存先として実装し、実際の API で速さを測りました（セッション開始 約2.1秒、読み書き 0.2〜0.7秒）。
  - 試したうえで、今の範囲では利点が表に出ないため、既定にはしていません。デモと評価はローカルの JSON を使い、`KOKOROE_STORE=memory` でメモリストアに切り替えられます。

### Q. Claude Code を開発の中心にどう使いましたか。何が可能になりましたか

一人・一週間で、評価から公開・動画まで作れたのは、Claude Code に作業だけでなく**守る仕組み**を任せられたからです（詳細は `docs/how-we-built.md`）。

- **プランモード:** 初日、リポジトリの外の計画メモを読むだけにして計画を立て、評価を最初に作る順番を決めました。
- **フック:**
  - このリポジトリから MCP を呼べないようにしました（仕事用のコネクタが公開リポジトリに混ざらないように）。
  - 次のことを、すべて仕組みで守りました。
    - コミット前に秘密情報を検査する。
    - 隠しの正解を凍結し、チェックサムで検査する。
    - コアやプロンプトを変えるとテストが走り、小さな評価を回すまでコミットできない。
    - AWS は決まったプロファイルでしか呼べない。
- **サブエージェントの使い分け:**
  - `world-keeper` の定義に沿った general-purpose のサブエージェントが、学習用40場面を並行して作りました（途中で作ったプロジェクトのサブエージェントは、再起動まで読み込まれないため）。
  - `ui-critic` はスクリーンショットだけを見て講評します。`judge-critic` は審査基準で提出物を読み、記録で裏付けられる改良だけを挙げます（`docs/ui-polish-log.md`）。
  - HITL と安全の係（hitl-reviewer）は、心得帳に書き込む変更をレビューします（原則コミット前。D-057 の絞り込みだけはコミット後）。最初の UI で重大なバグ3件、その後も自分の会社で始めるモードで4件、訪問の段取りで1件、次の案の先読みの競合2件（D-066）を、出す前に見つけました。
  - マイルストーンごとの監査は、独立した2つの係に任せました（`docs/audits/`）。
- **Skills:** 架空世界の一貫性と、決定の記録の型を Skill にしました。製品そのものも Agent Skill を書き出し、後任の Claude Code で読み込まれることを、リポジトリの外の空のディレクトリで確かめています。
- **ヘッドレス実行（`claude -p`）:** 後任の手元の Claude Code（Skill だけ／Skill ＋ MCP）を、同じ条件で再現して答えを記録しました。
- **思い込まずに測る:**
  - 変更のたびに、評価用場面で複数回測りました。
  - 同じ設定でも学習の道筋で10ポイント揺れると分かったので、数字は平均と幅で示すことにしました。
  - 正式な計測は `npm run eval:final` の1コマンドで行い、README の数字はその JSON から生成しています（手で書き写した数の誤りを見つけたのが、この仕組みにしたきっかけです）。
- **人が決めることは人に:**
  - 判断が要るところでは止まって作者に聞き、60件以上の決定記録（`docs/decisions.md`）に残しました。
  - AWS への変更と公開は、毎回、事前に OK を取りました。
- **二つ目の帳場:** 開発そのものも製品と同じ形で進めました。Claude Code の案に作者が一言で判断し、その違いを `CLAUDE.md`・フック・決定記録に残しています（README「二つ目の帳場」に、git の履歴と記録から拾った5つの例）。

### Q. 基本的な使い方を超えた点、新しい使い方は

- **AI に答えさせて、人には直させる。** 教えるのではなく「違う」と言うだけで、暗黙知が適用範囲と沿革つきのルールになります。
- **「なぜそうなったか」を残して渡す。** ルールだけでなく、旧 → 新、きっかけ、日付、師匠の言葉までを心得帳の本文に残し、Agent Skill として別の人の Claude Code に引き継ぎます。
- **写しと問い合わせ口の二段構え。** Skill はある時点の写しで、師匠の引退後も残ります。読み取り専用の MCP は、引き継ぎの期間に育ち続ける心得帳への窓です。
- **評価の作り方。** 師匠をシミュレータにし、判定はコードで機械的に行うので、LLM の採点の甘さに頼りません。正解は弟子のコードから読めないように、テストとフックで隔てています。

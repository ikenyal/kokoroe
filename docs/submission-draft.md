## 5. プロジェクト概要：解決する課題と、誰のためのものか *（500字以内）

<!-- overview:start -->
このプロジェクトは、引退を控えた中小企業のベテランの頭の中にしかない取引先ごとの作法を、AI の弟子の案に ○・△・× と、あれば一言で直すだけで、理由と経緯つきの心得帳として後任へ渡せるようにする道具です。

誰に先に伝えるか、正式な話の前に誰の耳に入れておくか。ベテランは聞かれても言葉にできませんが、案を見れば「違う」と言えます。引退が決まってから後任に渡すまでの数か月、師匠は毎日、弟子の案に印を付けるだけです。直しは Claude が読み取り、適用範囲と経緯つきの心得になり、次の案から効きます。後任が「遅延の連絡は確定してからでいいですか」と尋ねると、心得帳だけを根拠に理由と経緯を添えて答え、記録にないことには「師匠に確認を」と返します。心得帳は Agent Skill として後任の Claude Code に渡せます。架空のデータ（取引先10社）で、シミュレータの師匠が学習用40場面に約119回タップ（印・候補の選択・なぜ？・確かめ）すると、評価用20場面で ○ が付く案が54%から71%に、後任が経緯ごと答えられた質問が8問中0から5.2問になりました。

## 9. 開発中に一番詰まった場面 *（①何を作ろうとしていたか ②Claude にどう指示したか ③何が起きたか ④期待と何が違ったか ⑤どう対処したか）

**訪問の段取りの指示が、連絡の段取りそのものを動かした**（Kento 11/6 に選んだもの）

- ① 段取りに訪問が入るとき、服装・手土産・同席者なども案に含めたかった。
- ② 弟子への指示（システムプロンプト）に訪問の段落を足し、答えの形も一つにまとめて、一度の呼び出しで両方を書かせた。
- ③ 訪問を入れてデモを録り直すと、架空の取引先・丸新酒造（窓口は奥様、決裁は蔵元）の最初の案が「蔵元を表に、奥様を裏に」になった。師匠が直して心得ができるはずの場面で何も学ばれず、デモの筋が崩れた（1回、≈ $0.52）。
- ④ 訪問の指示は、訪問の欄だけに効くと考えて設計していた。実際には連絡の宛先の判断まで変え、アプリの弟子（訪問あり）と評価される弟子（訪問なし）が別の弟子になって、評価が製品を表さなくなった。
- ⑤ 段取りは常に評価と同じ呼び出し（1バイトも変えない）で作り、訪問の段取りは、決まった段取りを引用データとして受け取る2回目の呼び出しに分けた。2回目の答えの形には段取りの欄がなく、段取りを変えられない。評価の呼び出しが変わっていないことはテストで確かめる。

## 11. Claude を使った感想と改善してほしい点 *

### ① 日本語や日本の業務で使う立場から気づいた欠点と利点（具体例）

利点は、取引先台帳から、日本の商慣習に沿った丁寧でもっともらしい段取りと文面を作れることです。ただ、それは裏返しでもあります。作者が初見で印を付けたところ、20件中18件が合格に見えましたが、シミュレータの正解では、そのうち15件は直すべき案でした（架空のデータ）。経緯を知らない人には、もっともらしさが誤りを見えにくくします。欠点の例は、訪問の段取りを頼む指示を足しただけで、「奥様が窓口、蔵元が決裁」という宛先の判断まで逆になったこと、後任への答えに心得帳の内部の書き方（記号や番号）がそのまま出たことです。どちらも指示を分けたり言葉を指定したりして直しました。

### ② 他の AI ツールと比べて劣る点と優れる点

普段は ChatGPT、Codex、Kiro も併用しています。今回いちばん違ったのは、チャットの Claude と Claude Code を組み合わせて、「相談して判断する役」と「実装して確かめる役」に分けられたことです。チャットの Claude が計画や判断の整理、Claude Code への指示づくりを受け持ち、Claude Code はフック、サブエージェント、Skills で決まりを守りながら、長い時間、自分で講評と改良を回しました。作者は監督に専念できました。比べて劣ると感じた点は、特にありませんでした。利用の上限や会話の圧縮で長い作業が途切れうることはありましたが、これはどのツールにも共通の課題だと感じています。

### ③ 一つだけ直せるとしたら何か、その改善で何が作れるようになるか

人間の理解が追いつかないことです。Claude Code は、15分ごとに講評と改良を回し、一晩で何十もの変更を積み上げました。速さは大きな価値ですが、何が変わり、何を自分が判断すべきかを追うのが、人間の側でいちばん大変でした。直せるなら、作業の速さを落とさずに、「今、人が判断すべきこと」と「変わったことの要点」を、人の理解の速さに合わせて届ける仕組みがほしいです。たとえば、変更の一つ一つに人が ○・△・× と一言を付けると、その違いが CLAUDE.md に残り、次から Claude Code の判断がその人に近づいていく形です。これは Kokoroe が取引先の付き合い方でやったことと同じ形で、開発でも、プログラマーではない人が、AI の速さを保ったまま安心して監督できるようになります。

### 5. プロジェクト概要（487字。500字以内。改行は数えない）
```text
このプロジェクトは、引退を控えた中小企業のベテランの頭の中にしかない取引先ごとの作法を、AI の弟子の案に ○・△・× と、あれば一言で直すだけで、理由と経緯つきの心得帳として後任へ渡せるようにする道具です。

誰に先に伝えるか、正式な話の前に誰の耳に入れておくか。ベテランは聞かれても言葉にできませんが、案を見れば「違う」と言えます。引退が決まってから後任に渡すまでの数か月、師匠は毎日、弟子の案に印を付けるだけです。直しは Claude が読み取り、適用範囲と経緯つきの心得になり、次の案から効きます。後任が「遅延の連絡は確定してからでいいですか」と尋ねると、心得帳だけを根拠に理由と経緯を添えて答え、記録にないことには「師匠に確認を」と返します。心得帳は Agent Skill として後任の Claude Code に渡せます。架空のデータ（取引先10社）で、シミュレータの師匠が学習用40場面に約119回タップ（印・候補の選択・なぜ？・確かめ）すると、評価用20場面で ○ が付く案が54%から71%に、後任が経緯ごと答えられた質問が8問中0から5.2問になりました。
```

### 9. 開発中に一番詰まった場面（486字）
```text
訪問の段取りの指示が、連絡の段取りそのものを動かした（Kento 11/6 に選んだもの）

- ① 段取りに訪問が入るとき、服装・手土産・同席者なども案に含めたかった。
- ② 弟子への指示（システムプロンプト）に訪問の段落を足し、答えの形も一つにまとめて、一度の呼び出しで両方を書かせた。
- ③ 訪問を入れてデモを録り直すと、架空の取引先・丸新酒造（窓口は奥様、決裁は蔵元）の最初の案が「蔵元を表に、奥様を裏に」になった。師匠が直して心得ができるはずの場面で何も学ばれず、デモの筋が崩れた（1回、≈ $0.52）。
- ④ 訪問の指示は、訪問の欄だけに効くと考えて設計していた。実際には連絡の宛先の判断まで変え、アプリの弟子（訪問あり）と評価される弟子（訪問なし）が別の弟子になって、評価が製品を表さなくなった。
- ⑤ 段取りは常に評価と同じ呼び出し（1バイトも変えない）で作り、訪問の段取りは、決まった段取りを引用データとして受け取る2回目の呼び出しに分けた。2回目の答えの形には段取りの欄がなく、段取りを変えられない。評価の呼び出しが変わっていないことはテストで確かめる。
```
### 10. 公式の情報（311字）
```text
おおむね見つけられました。Managed Agents のメモリストアは、Claude Code に入っている Claude API の Skill から公式の情報を読み、SDK のメソッドとベータヘッダーを確かめてから試作しました。メモリストアがワークスペース単位であることや、版の扱いも公式ドキュメント（Using agent memory）で確かめ、事前の計画メモの思い込みを公式の記述に合わせて直しました。Next.js 16 は、パッケージに同梱されたドキュメントを読んで書きました。一方で、Managed Agents はベータで情報が少なく、手元で実際に呼び出して速さや挙動を測って確かめる必要がありました。
```
### 11 ① 日本語や日本の業務で使う立場から（283字）
```text
利点は、取引先台帳から、日本の商慣習に沿った丁寧でもっともらしい段取りと文面を作れることです。ただ、それは裏返しでもあります。作者が初見で印を付けたところ、20件中18件が合格に見えましたが、シミュレータの正解では、そのうち15件は直すべき案でした（架空のデータ）。経緯を知らない人には、もっともらしさが誤りを見えにくくします。欠点の例は、訪問の段取りを頼む指示を足しただけで、「奥様が窓口、蔵元が決裁」という宛先の判断まで逆になったこと、後任への答えに心得帳の内部の書き方（記号や番号）がそのまま出たことです。どちらも指示を分けたり言葉を指定したりして直しました。
```

普段は ChatGPT、Codex、Kiro も併用しています。今回いちばん違ったのは、チャットの Claude と Claude Code を組み合わせて、「相談して判断する役」と「実装して確かめる役」に分けられたことです。チャットの Claude が計画や判断の整理、Claude Code への指示づくりを受け持ち、Claude Code はフック、サブエージェント、Skills で決まりを守りながら、長い時間、自分で講評と改良を回しました。作者は監督に専念できました。比べて劣ると感じた点は、特にありませんでした。利用の上限や会話の圧縮で長い作業が途切れうることはありましたが、これはどのツールにも共通の課題だと感じています。

### 11 ③ 一つだけ直せるとしたら（350字）
```text
人間の理解が追いつかないことです。Claude Code は、15分ごとに講評と改良を回し、一晩で何十もの変更を積み上げました。速さは大きな価値ですが、何が変わり、何を自分が判断すべきかを追うのが、人間の側でいちばん大変でした。直せるなら、作業の速さを落とさずに、「今、人が判断すべきこと」と「変わったことの要点」を、人の理解の速さに合わせて届ける仕組みがほしいです。たとえば、変更の一つ一つに人が ○・△・× と一言を付けると、その違いが CLAUDE.md に残り、次から Claude Code の判断がその人に近づいていく形です。これは Kokoroe が取引先の付き合い方でやったことと同じ形で、開発でも、プログラマーではない人が、AI の速さを保ったまま安心して監督できるようになります。
```
